READ THIS BEFORE READING ANY NUMBER ABOVE: THE MOCK PATH ECHOES LABELS, IT DOES NOT REASON.

  The mock backend in completion-continuation-accuracy-harness.ts maps the hand label straight to a
  probability: true -> 0.95, false -> 0.05, unknown -> 0.50. It never looks at the state, so it never
  looks at the new previous block either. The after-state above is therefore a readout of the labels
  plus the plumbing that carries them, nothing more.

  WHAT THE MOCK PATH DOES ESTABLISH
    1. All five label corrections are wired through end to end: exactly 5 of 54 question-by-fixture
       rows moved, all on progressing, all false -> true, and they are precisely the five fixtures
       todos 2 and 2-followup corrected.
    2. The consistency guard holds: the fixture-label consistency test is green, so no label
       contradicts the W2 plan line-45 ground-truth rule.
    3. Nothing else drifted: actually_complete and stuck are unchanged in every single metric,
       which is the expected blast radius of a progressing-only label correction.
    4. The threshold is untouched at 0.8 on both sides, and no accuracy gate was introduced.

  WHAT THE MOCK PATH CANNOT ESTABLISH, AND MUST NOT BE READ AS ESTABLISHING
    The progressing band moving from 8 would_true to 13 would_true is NOT evidence that the
    delta-input fix works. A label-echoing backend has no ceiling to lift, so the improvement is
    arithmetic from the corrected labels, not reasoning from the previous block. The root cause this
    plan identified, that we asked a delta question while withholding the delta, remains UNMEASURED.
    Only a real-API run can measure it, and that run is deliberately deferred to the blocked todo 7.
