    Why I agree:
      a) Neither file is on the plan's forbidden list. The list names
         JevWireConfigSchema and "any W4 file"; the plan's own operationalization of
         the W4 rule is byte-identity of the two W4 TEST files plus untouched
         model-error-triage.ts, and all three hold.
      b) Type-level only. Zero runtime code. JsonValue is pre-existing
         (types.ts:61), so no new vocabulary was invented.
      c) I independently verified backward compatibility rather than accepting the
         claim. Every consumer of ChoiceQuestion.criteria was enumerated:
         answer-validation.ts:52 uses `answer.choice in question.criteria` (key
         membership, value never read) and :61 uses Object.keys. The value-equality
         read at :100 is on ScoreQuestion, whose criteria is an array and is
         untouched. No existing code reads a ChoiceQuestion criteria VALUE, so
         widening it breaks no reader.
      d) The need is real: intent-routing.test.ts:96-120 shows the new questions
         carry structured object criteria ({ description: ... }), which the old
         `string | null` literally could not express. Todo 4 mandates the SDK's
         structured criteria capability.
      e) sdk-type-compat.test.ts moving from `string | null` to `Sdk.Description`
         is the correct direction for a file whose whole purpose is asserting our
         local types stay assignable to the vendor SDK types.
    Residual caveat I am recording, not rejecting on: types.ts is shared jev-core
    infrastructure that W4 also imports, so a maximally literal reading of "any W4
    file" could sweep it in. I do not read it that way, for reason (a).

D2. packages/omo-opencode/src/plugin/tool-execute-before.ts
    VERDICT: I AGREE on the SUBSTANCE. IN SCOPE. Not a reject.
    BUT THE DISCLOSURE AS WRITTEN IS INCOMPLETE. Recording that separately.
    The disclosure says the file "gained an optional intentRoutingCapture? param
    plus one optional-chained call". The actual diff is larger:
      i)   a SECOND new parameter, pluginConfig?: OhMyOpenCodeConfig
      ii)  a live fallback construction executed at handler-factory time:
             const intentRoutingCapture = args.intentRoutingCapture
               ?? createJevIntentRouting({ jevConfig: args.pluginConfig?.jev })
      iii) the call itself, intentRoutingCapture?.capture(input, output), where the
           local is non-optional after the ??, so the ?. is vestigial (harmless)

    Why the substance is still in scope:
      a) C3 explicitly mandates ground-truth capture at tool.execute.before for
         both task and call_omo_agent. Capturing here is the assignment.
      b) The `?? createXxx(...)` fallback is NOT a new invention. It exactly mirrors
         the pre-existing W4 precedent in plugin/event.ts:
           const jevTriage = args.jevTriage ?? createJevModelErrorTriage({...})
