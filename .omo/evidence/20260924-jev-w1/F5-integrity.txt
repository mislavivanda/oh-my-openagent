-- ASSERTION 6: NO DOUBLE-COUNT BETWEEN records_evicted AND ANY sealedBy VALUE -- PASS

Type-level: SEALED_BY_VALUES in script/jev-w1-report.ts:16 is exactly
  ["next_turn", "session_idle", "seal_timeout", "dispose", "session_deleted"]
and script/jev-w1-report.fixtures.ts:18 pins it as

No eviction is reachable through any sealedBy bucket. PASS.

Honest caveat: on the LIVE corpus records_evicted is 0, so the live run alone would have
demonstrated this only vacuously. The non-vacuous proof is the FIXTURE corpus.

-- ASSERTION 9: none RECALL AND none PRECISION, BOTH PRESENT, CORRECTLY LABELLED,
   ON DIFFERENT CONDITIONING SETS -- PASS, AND THEY DIFFER ON THIS CORPUS

DERIVED corpus (F5's own live data):
  none_recall:    15/15 = 100.00% (eligible_denominator=15)
  none_precision: 15/28 = 53.57%  (eligible_denominator=28)

Conditioning sets, from script/jev-w1-report.ts:153-164:
  recall    denominator = actualNone    = rate-eligible AND knownRoutes.size === 0 AND !hasUnknown
                                        = turns that ACTUALLY had zero scorable routes.   n=15
  precision denominator = predictedNone = rate-eligible AND predictedRoute === "none"
                                        = turns where none was PREDICTED.                 n=28
  shared numerator = isValidNone = the intersection (predicted none AND actually none, valid,

They are NOT numerically equal on my corpus: 100.00% vs 53.57%, denominators 15 vs 28.
The FIXTURE corpus also separates them: none_recall 1/1 = 100.00%, none_precision 1/3 = 33.33%.
The earlier draft's mislabelling of recall as precision is definitively fixed, and I did not have
to rely on equality-as-proof.

Additional correctness the labels get right, shown by MINPAIR: for a single unknown-only record,

correct - an unknown-only turn is not a turn that "actually had zero scorable routes" in the
representable sense (the !hasUnknown guard), so it is properly kept out of the recall denominator
while still being charged against precision and route agreement.

== FINDINGS ==

F-1  SEVERITY HIGH (blocking).  The documented report command cannot produce a report on the
     corpus its own documented driver produces. Timing-dependent, so a green result elsewhere is
     luck rather than proof.

     Observed: bun run script/jev-w1-report.ts --root "$F5_SANDBOX/home/.omo/jev"
               -> ReportIdentityError: records_created 30 is less than sealed 33 plus evicted 0

     Root cause, proven from the corpus and the source:
       INTENT_ROUTING_SINK_COUNTER_INTERVAL_MS = 60_000
         (packages/omo-opencode/src/features/jev/intent-routing-sink-config.ts:8)
       The counter snapshot is flushed by setInterval(emitCounterDelta, 60s) plus once in
       dispose() (intent-routing-sink.ts:179-191). The driver SIGTERMs the opencode server
       (task-19-drive.sh:248), so dispose() never runs and no final snapshot is written.

     Timing proof from my own sink file:
       obs ordinal 1   recordedAt 2026-09-24T19:14:52.630Z
       counter_delta   recordedAt 2026-09-24T19:15:48.071Z  monotonicSeq=1  recordsCreated=30
       obs ordinal 31  recordedAt 2026-09-24T19:15:48.818Z   <- 0.75s AFTER the snapshot
       obs ordinal 33  recordedAt 2026-09-24T19:15:51.065Z
       file layout: lines 1-30 observations, line 31 counter_delta, lines 32-34 observations
       monotonicSeq=1 means this was the FIRST and ONLY tick; a dispose() flush would be seq=2.

     Why it is timing-dependent: the driver's post-turn wait loop (task-19-drive.sh:243-247) breaks
     as soon as ANY counter_delta exists. If the turns finish in under 60s the single tick lands
     AFTER all turns and the snapshot is complete, so the report succeeds. My run took 58.4s of
     turn wall-clock and the tick landed 3 records before the end, so it failed. The pipeline is
     therefore flaky by wall-clock, and the report's response to the flake is to abort rather than
     to degrade.

     Note the writer already defends against exactly this under-count internally -
     accountObservation() floors recordsCreated at retainedObservations + recordsEvicted
     (intent-routing-sink.ts:109-112) - but the reader applies no equivalent floor, so it trusts a
     snapshot the format does not guarantee is current.

     This is a defect, reported not fixed.

F-2  SEVERITY HIGH.  The identity is a tautology, not a reconciliation, and the second check is
     dead code.

     script/jev-w1-report.ts:176-179
       const inFlight    = counters.recordsCreated - sealed - counters.recordsEvicted
       if (inFlight < 0) throw ...
       const identityTotal = sealed + counters.recordsEvicted + inFlight
       if (counters.recordsCreated !== identityTotal) throw ...

     Substituting the definition of inFlight, identityTotal is
       sealed + evicted + (created - sealed - evicted) === created
     for all integer inputs. The line-179 comparison can therefore NEVER be false, and the printed
     line "identity: records_created(30) == sealed(30) + evicted(0) + in_flight(0)" restates a
     definition rather than reconciling two independently-sourced quantities.

     The only live check is inFlight < 0, which catches UNDER-counting only. An OVER-count
     (records_created larger than reality) is silently absorbed into records_in_flight, where it is
     indistinguishable from genuinely in-flight records. A reader is invited by the word "identity"
     to read the line as evidence of reconciliation; it is not.

F-3  SEVERITY HIGH.  Six reported denominators are hard-coded to zero in the live path. The report
     prints un-instrumented zeros in the same list, same format, as genuinely measured counts.

     Source proof, packages/omo-opencode/src/features/jev/intent-routing-turn-record.ts
     buildStoreCounterDelta(), which is what the live turn store emits:

       turnsSeen: 0,                 <- literal
       turnsGatedOut: 0,             <- literal
       turnsSynthetic: 0,            <- literal
       recordsCreated: input.recordsCreated,        <- real
       recordsEvicted: input.recordsEvicted,        <- real
       orphanObservations: input.orphanObservations,<- real
       unscorableResumeCalls: 0,     <- literal
       unscorableUnknownCalls: 0,    <- literal
       dispatchesDropped: 0,         <- literal

     Only three of the counters are threaded through. rebaseCorpusCounters propagates the rest as
     Math.max(0, 0 - 0) = 0, so turns_seen, turns_gated_out, turns_synthetic,
     unscorable_resume_calls, unscorable_unknown_calls and dispatches_dropped can never be non-zero
     in a live run, regardless of what actually happened.

     Empirical smoking gun - the report contradicts itself on my own live corpus:
       unscorable_resume_calls: 0        <- from the counter snapshot
       resume_only_records: 2            <- derived from the rows
       and 2 observations with routeClass "unscorable_resume" are physically on disk
       (routeClass histogram: category 11, subagent 9, unscorable_resume 2)
     Likewise turns_seen: 0 is printed next to records_sealed: 30.

     The FIXTURE corpus masks this completely, because writeSyntheticCorpus hand-writes counter
     deltas with turnsSeen 25, turnsGatedOut 3, unscorableResumeCalls 3 and so on. So
     fixture-backed tests are green on denominators that are structurally dead in production.

     This is squarely a "numbers are honest" failure: a reader cannot distinguish "measured zero"
     from "never instrumented", and in the resume case the two printed numbers cannot both be true.

F-4  SEVERITY MEDIUM.  The none-heavy fixture denominator is derivable but never disclosed, and the
     premise I was given understates it.

     Actual label distribution in packages/jev-core/src/intent-routing-fixtures.ts:
       label.category "none" = 8 of 15   (my instructions said 6)
       label.subagent "none" = 13 of 15
     A constant "none" predictor therefore scores 8/15 category and 13/15 subagent with zero
     capability, which materially flatters the headline 48/60 = 80.0%. task-18-real-api-matrix.txt
     supplies the raw material to compute this but states no base rate, offers no majority-class
     baseline, and attaches no caveat to the 80% figure. Not dishonest; under-disclosed.

F-5  SEVERITY LOW-MEDIUM.  The driver's own cross-check is race-prone at shutdown and failed on
     this run.

       FAIL: Jev dispatches (32) do not match intent logs (31)

     task-19-drive.sh compares fake-Jev request count against plugin-log line count (lines 256-257,
     asserted at 270) AFTER SIGTERMing the server (line 248). A dispatch that reached the fake Jev
     while the plugin's log write lost the race with termination produces exactly this off-by-one.
     Same shutdown-ordering family as F-1. It makes the driver exit non-zero on a run whose corpus
     was otherwise complete (33/33 observations sealed, single session, all fan-out buckets
     populated), which will intermittently fail any lane that treats driver exit status as a gate.


== WHY THIS IS ENOUGH ==

Assertions 6, 7, 8, 9, 10, 11, 12 and 13 are each verified with a concrete printed number, and the
three that the live corpus could not exercise non-vacuously (eviction double-count, censored /
overlap exclusion, unknown-vs-resume) are proven on the repo's own committed fixture corpus and on
a hand-minted minimal pair rather than asserted from code reading alone. Assertion 5 is verified as
failing, with a timestamp-level root cause. The accuracy figures in assertion 14 were re-derived
from the raw confusion matrices and tie out to the last digit.

Residual risk not covered: I exercised one live run on one machine. F-1 is timing-dependent, so the
exact 30-vs-33 split is not reproducible, but the mechanism (60s tick, no dispose flush on SIGTERM)
is structural and will recur. I did not measure how often a sub-60s run masks it.
