CHECK 9 - do the tests assert real behavior, or mirror the implementation?
  I read three files end to end and judged whether each would actually catch a regression.

  (a) packages/omo-opencode/src/plugin/intent-routing-runtime-effects.test.ts (206)  WOULD CATCH
      Asserts against an independently-held ground truth, not against the implementation's own
      bookkeeping. It drives 50 real turns through the real chat.message handler with the real
      dispatcher and real sink against a backend that never resolves, and pins:
      maxFetches === MAX_INFLIGHT and activeFetches === MAX_INFLIGHT (counted by the injected fetch
      itself, outside the code under test), dispatchesDropped === TURN_COUNT - MAX_INFLIGHT (48, an
      exact arithmetic value, not "greater than zero"), max per-handler latency < 50ms, added total
      latency < 50ms measured against a disabled-wire control run of the same 50 turns, and heap
      growth < 16MB. Remove the in-flight cap and maxFetches/activeFetches break. Make the handler
      await the prediction and maxHandlerMs blows past 50ms instantly, since the backend never
      resolves. Leak a ref'd timer and the second test fails: it spawns a real child process with
      the real wire and a hanging fetch and requires exit code 0 within 1500ms, having first proven
      the fetch actually started (stdout marker child_fetch_started=1). That child test is the only
      honest way to prove "unrefed timers let the process exit" and it does it properly.
      It also pins the sink path under the temp root, so a regression writing outside the sandbox
      fails here.

  (b) packages/omo-opencode/src/features/jev/intent-routing-turn-store.test.ts (373) WOULD CATCH
      The strongest file of the three. It counts dispatches with an external counter and asserts
      exact integers, which is what distinguishes a real cache test from a mirror. Tier-1
      coalescing: two identical prompts -> dispatches === 1 and both ordinals resolve to the same
      answers. Tier-2 completed reuse on a pinned model -> dispatches === 1 and predictionReused
      true. The floating-alias case is the one that proves real thought: with model "jev-latest" and
      no known resolution, reuse is DISABLED and dispatches === 2, but with currentResolvedModel
      supplied it re-enables and drops back to 1. That is a correctness trap most implementations
      get wrong, and the test would catch silently reusing a prediction made by a different
      underlying model. Negative paths are covered with exact counts too: failed predecessor -> 2,
      timed-out predecessor -> 2 plus the predecessor observably transitions to "timeout",
      not-dispatched predecessor -> 1, evicted predecessor -> 3. A table-driven loop proves each of
      questionVersion / vocabularyDigest / confidenceThreshold / configuredModelSpec is actually
      load-bearing in the dedup key, so dropping any one from the key fails a specific case.
      Eviction is pinned to exact survivors ([6,7,8]), an exact evictedCount (5), and a durable
      counter_delta entry, so a silent eviction leak is caught. The seal/LRU-exemption pair is the
      subtle one and both directions are pinned, including the "exemption prevents premature
      finalization" case that asserts NO observation is emitted early and then that the eventual
      observation carries sealedBy "next_turn" and correlationStatus "reliable". Normalization is
      tested for both collision (padding/casing/system-reminder stripping collide) and
      non-collision (trailing "!" does not), which catches an over-aggressive normalizer.
      Ordinal minting is asserted distinct even when the dedup key is shared.

  (c) packages/jev-core/src/intent-routing-accuracy.test.ts (479)                   WOULD CATCH
      Asserts the harness's safety envelope rather than a score, which matches the plan's
      measure-do-not-gate intent. Real regressions it catches: dry-run performing any backend or
      network call (artifact pinned to zero calls); selectRunMode mis-routing across the four
      JEV_W1_REAL_API / TYPESAFE_API_KEY combinations, including the important "real flag set but no
      key still selects real (and short-circuits)" case; the call ceiling failing to abort, which is
      pinned hard by putting the counter one below the ceiling and asserting the run rejects with
      IntentRoutingCallCeilingError with backendCalls frozen at the pre-second-call value; and
      partial-artifact integrity on failure, where a backend failure at fixture eight must leave
      exactly the first seven fixture ids. The completion test pins artifact.status, that the
      confusion matrices cover exactly QUESTION_IDS, and full fixture coverage.
      Honest weakness: several assertions in the final test are conditional on mode, so the
      "real" branch never executes in CI (mock mode), and there is deliberately no accuracy
      threshold. That is by design, but it means this file proves the harness is safe and
      well-formed, not that routing quality is good. The mock run visible in the suite output did
      score 15/15 exact and 60/60 answers, which is a measurement, not a gate.

  Overall: these are behavior tests, not implementation mirrors. The recurring pattern is an
  externally-held counter or an independently-computed control run, compared with exact integers.
  Weakest link is the mode-conditional block in (c), which I record as informational.
