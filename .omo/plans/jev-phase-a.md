**What you'll get:** A new, self-contained Jev decision layer for omo that is switched off by default: a typed way to ask TypeSafe's Jev model a question and get a calibrated answer back (with a real client, a test double, and a reserved slot for an LLM stand-in), a config block to turn it on, and the first live use of it: when a model call fails, Jev decides whether omo should retry on another model, stop because the account is exhausted, or ignore the error, and omo only follows Jev when Jev is confident. Everything else keeps behaving exactly as today. Your handoff document is committed and corrected, a dogfood log is started, and every check is recorded as evidence.

**Why this approach:** Additive and default-off, so the fork stays trivially mergeable with upstream and the maintainer can review one small, provable change. Jev sits behind a fallthrough: any timeout, missing key, low confidence, or bad response silently yields to the existing heuristic, which is what makes it safe to ship dark and to A/B later. The new code lives in its own harness-neutral package so the Codex edition can reuse it and the third-party SDK dependency has exactly one home.

**What it will NOT do:** No other decision wires (intent gate, completion gauntlet, stall detection, keyword triggers) and no benchmark harness yet. It never changes behavior unless you turn it on, never reads an API key from a config file, and never touches the other four places the old retry heuristic is used. Nothing is pushed or opened as a PR; the work is built in a separate sibling working copy of the repository (so your current checkout is never edited mid-flight) and lands on your local foundation branch only after you say so.

**Things you did not ask for that are included anyway (each is small, and you can veto any):** the TypeSafe client library is loaded when the plugin starts even while Jev is off (it is inert until enabled, but it does ride along in the shipped bundle); all three Jev question types are typed up front, not just the one this phase uses, so later phases do not reshape the foundation; a quick test shortcut command is added to the repository; if a Jev API key happens to be present in your shell, three real one-off calls are made to Jev and their results are recorded as evidence (skipped when no key is set, which is the case on this machine); and the new triage only ever engages when omo's existing model-fallback feature is also switched on, which it is not by default.

**Risk:** Medium - one third-party SDK enters the shipped bundle, and the repository's own package-registration and markdown audits fail loudly on any missed registration, so most mistakes surface as red tests rather than silent breakage.

## Execution strategy
### Parallel execution waves
> Target 5-8 todos per wave. Fewer than 3 (except the final) means you under-split.

Waves are dependency-cut; several are deliberately small because each carries a gate (baseline red-stop, human checkpoint, checkpoint commit). Within a wave, todos may run in parallel via delegated subagents ONLY when they touch disjoint files AND their acceptance gates are disjoint (a gate such as `bun test packages/jev-core` or `./node_modules/.bin/tsgo --noEmit -p packages/jev-core/tsconfig.json` covers the whole package, so two todos editing `packages/jev-core` can never run in parallel: one's half-written file would fail the other's gate, and one's tests would satisfy the other's). The ONE deliberate exception to "disjoint files" is `$EVIDENCE_DIR/MANIFEST.tsv`, which every todo appends to: parallel todos in a wave (2/3/4, 10/11, 13/14) may append concurrently ONLY because each row is a single `printf` of one short line (well under a page) to a file opened with `>>` (`O_APPEND`): `O_APPEND` positions and writes atomically per `write(2)` on a local Linux filesystem, and `strace` shows both bash and dash emit exactly one `write(2)` per `printf` row, so rows cannot interleave (this is NOT a `PIPE_BUF` guarantee, which applies to pipes; on a network filesystem where append semantics are uncertain, the lead session records the rows itself instead); a todo must never rewrite or sort the manifest in place while a sibling may be running (only F1 reads it, and only after wave 12 is sequential again). If a delegated subagent cannot guarantee single-`printf` rows, the lead session records that todo's rows itself after the subagent returns.
